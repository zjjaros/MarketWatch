# MarketWatch Command Reference

This document contains commonly used commands for local development, Docker, Terraform, and AWS operations.

Commands assume Windows PowerShell unless otherwise noted. Replace placeholders such as `<instance-id>` and `<repository-uri>` with the appropriate values from your AWS environment.

## Local Development

Run these commands from the repository root unless otherwise noted.

### Activate the Python environment

```powershell
.venv\Scripts\Activate.ps1
```

If the virtual environment has not been created yet:

```powershell
uv sync
```

### Run the API locally

```powershell
uv run uvicorn api.main:app --reload
```

Open the interactive API documentation at:

- http://127.0.0.1:8000/docs

> Adjust the module path if the API entry point changes.

### Run the collector locally

```powershell
uv run python -m collector.main
```

The collector retrieves market data from configured providers and writes observations to PostgreSQL. Ensure the database is available and configured before starting it.

### Run Python commands through uv

```powershell
uv run python --version
uv run pytest
```

The test command assumes a test suite is configured.

## Database and Migrations

MarketWatch uses PostgreSQL, SQLAlchemy, and Alembic for database persistence and schema migrations.

### Apply pending migrations

```powershell
uv run alembic upgrade head
```

### Check the current migration

```powershell
uv run alembic current
```

### View migration history

```powershell
uv run alembic history
```

### Generate a migration from model changes

```powershell
uv run alembic revision --autogenerate -m "describe schema change"
```

Review autogenerated migration files before applying them. Autogeneration may not detect every schema change or data migration correctly.

### Roll back one migration

```powershell
uv run alembic downgrade -1
```

**Caution:** Downgrading a migration may remove schema objects or data. Review the migration before running this command against a database containing important observations.

## Docker and Docker Compose

Run these commands from the directory containing `compose.yaml`.

### Start the application stack

```powershell
docker compose up -d
```

### Rebuild images and start services

```powershell
docker compose up -d --build
```

### View running containers

```powershell
docker compose ps
```

### Follow logs for all services

```powershell
docker compose logs -f
```

### Follow logs for a specific service

```powershell
docker compose logs -f api
docker compose logs -f collector
docker compose logs -f postgres
```

### Restart a service

```powershell
docker compose restart api
```

Replace `api` with `collector` or `postgres` as needed.

### Stop services

```powershell
docker compose stop
```

### Stop and remove containers and networks

```powershell
docker compose down
```

This does not ordinarily remove named volumes. Avoid adding `-v` unless you intentionally want to remove Compose-managed volumes, which may contain database data.

### Execute a command inside a container

```powershell
docker compose exec api sh
```

For PostgreSQL, if the container includes `psql`:

```powershell
docker compose exec postgres psql -U <db-user> -d <db-name>
```

Use the actual database username and database name from your configuration.

## Terraform and Infrastructure

Run these commands from the directory containing the relevant Terraform configuration.

### Initialize Terraform

```powershell
terraform init
```

Run this after checking out the project or when provider/module configuration changes.

### Validate the configuration

```powershell
terraform validate
```

### Format Terraform files

```powershell
terraform fmt -recursive
```

### Preview infrastructure changes

```powershell
terraform plan
```

### Apply infrastructure changes

```powershell
terraform apply
```

Review the proposed plan before confirming. Applying Terraform can create, modify, or destroy AWS resources.

### Inspect Terraform-managed resources

```powershell
terraform state list
```

### Inspect a specific resource

```powershell
terraform state show <resource-address>
```

For example, substitute an address returned by `terraform state list`.

### Destroy infrastructure

```powershell
terraform destroy
```

**Caution:** Destroying infrastructure can interrupt services and delete resources. Database snapshots and recovery procedures should be considered before destroying the environment.

### Start and stop the project infrastructure

If using the repository's PowerShell helper scripts:

```powershell
.\up.ps1
```

```powershell
.\down.ps1
```

These scripts may perform additional project-specific steps, including database snapshot and recovery handling. Review the scripts before running them, especially before destroying resources.

## AWS and ECR

The examples below use the AWS region `us-west-2`.

### Verify AWS CLI credentials

```powershell
aws sts get-caller-identity
```

If you use a named AWS CLI profile, append:

```powershell
--profile <profile-name>
```

### List ECR repositories

```powershell
aws ecr describe-repositories --region us-west-2
```

### Authenticate Docker to Amazon ECR

Replace `<account-id>` with your AWS account ID.

```powershell
aws ecr get-login-password --region us-west-2 |
    docker login --username AWS --password-stdin <account-id>.dkr.ecr.us-west-2.amazonaws.com
```

If PowerShell causes issues with the pipeline, run the login command through `cmd.exe` or troubleshoot the shell invocation before retrying. Never paste or save the registry password manually.

### Build the application image

Run from the directory containing the application Dockerfile:

```powershell
docker build -t marketwatch .
```

### Tag an image for ECR

```powershell
docker tag marketwatch:latest <repository-uri>:latest
```

### Push an image to ECR

```powershell
docker push <repository-uri>:latest
```

The repository URI is available from the ECR repository details or Terraform outputs.

### List images in ECR

```powershell
aws ecr list-images --repository-name marketwatch --region us-west-2
```

## EC2 and Systems Manager

These commands help inspect and manage the EC2 instances used by the API and collector.

### List EC2 instances

```powershell
aws ec2 describe-instances --region us-west-2
```

### Find running instances

```powershell
aws ec2 describe-instances --region us-west-2 --filters "Name=instance-state-name,Values=running" --query "Reservations[].Instances[].[InstanceId,Tags,PrivateIpAddress,PublicIpAddress]" --output table
```

### Check Systems Manager managed instances

```powershell
aws ssm describe-instance-information --region us-west-2
```

An instance must be configured correctly and connected to Systems Manager to appear as a managed instance.

### Start a remote shell session

```powershell
aws ssm start-session --target <instance-id> --region us-west-2
```

This requires the appropriate IAM permissions and a functioning SSM connection.

### Send a command to an instance

```powershell
aws ssm send-command --instance-ids <instance-id> --document-name "AWS-RunShellScript" --parameters commands="docker ps" --region us-west-2
```

The command returns a command ID. Use it to retrieve execution status and output.

### Check a command's status

```powershell
aws ssm get-command-invocation --command-id <command-id> --instance-id <instance-id> --region us-west-2
```

### View recent EC2 system logs

```powershell
aws ec2 get-console-output --instance-id <instance-id> --latest --region us-west-2
```

Console output is primarily useful for boot and operating-system troubleshooting; it does not replace application logs.

## Operational Notes

- **Review before applying:** Terraform plans and database migrations can have destructive consequences.
- **Protect persistent data:** Confirm snapshot and recovery procedures before destroying infrastructure or removing Docker volumes.
- **Use least privilege:** AWS commands require permissions appropriate to the resource and operation.
- **Keep secrets out of source control:** Do not commit database passwords, access keys, tokens, or populated secret files.
- **Check logs before restarting:** Container and SSM logs often reveal the cause of a failed deployment or collector run.
- **Use the correct environment:** Local development, test environments, and production infrastructure may have different credentials, endpoints, and configuration.
